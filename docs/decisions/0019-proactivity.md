# 0019: Proactivity

Status: accepted

Date: 2026-11-19

Spec #97 (Proactivity), tickets #102 (the default Brief), #100 (Outcome), and #105 (Less of this). Builds on [0013](0013-schedules-and-time.md), [0014](0014-schedule-actions.md), [0015](0015-scheduled-task-turn.md), [0016](0016-scheduled-task-failure-and-lateness.md), [0017](0017-scheduled-task-limits.md), and [0018](0018-reminder-failure-completes-the-schedule.md). It supersedes only one rule of [0007](0007-typed-queries-and-migrations.md) (see Schema file). Reminders and Scheduled Tasks that the Owner sets do not change.

## Decision

- **Open Loop.** An Open Loop is optional metadata on a Note: a free-text kind, a state (`open`, or `closed` with the reason `done`, `dropped`, or `replaced`), and an optional due date. A fact has no Open Loop. Habits, chores, and external items are later kinds. The design does not block them.
- **Proactive Message.** A Proactive Message comes from a Schedule with `setBy: agent`. Owner-set Reminders and Scheduled Tasks are not Proactive Messages. Every Proactive Message records an Outcome.
- **Outcome.** The Outcome is what the Owner did with a Proactive Message: `acted`, `replied`, `muted`, or `ignored`. It is evidence for the agent, not a stop rule in code. Code keeps only the hard limits: Quiet Hours, the Budgets, and "less of this".
- **One gate.** One module decides every `ScheduleFired` Event of a Schedule with `setBy: agent` before any model call: `Send`, `Hold`, or `FoldIntoBrief`. It holds a message in Quiet Hours, keeps the daily send Budget, merges messages that are due close together, and keeps the daily token Budget `proactiveDailyTokenBudget`. Owner-set Schedules never reach it. Tickets #99 to #105 build it step by step.
- **Defaults.** Quiet Hours 22:00 to 08:00, 3 sends per day, the Brief at the end of Quiet Hours, a response window of 24 hours, a merge window of 30 minutes, 200000 proactive tokens per day, and 20 active agent Schedules. They are first guesses.
- **Quiet Hours and Budget as Owner Preferences.** The Owner changes them in the chat. Each stored value records its source: `owner` now, and later a Profile or an integration.
- **The Brief.** When the time zone of the Owner becomes known, code creates the Brief once: a Daily `RunPrompt` Schedule with `setBy: agent` at the end of the default Quiet Hours, in the Owner's time zone. A `BriefCreated` Journal Entry records it. The identity of the Brief is its `BriefCreated` Journal Entry, which survives an edit of its prompt. Code also looks for an agent-set Schedule with the Brief prompt, in any state, so a Schedule without its entry after a reset still counts. A second time zone change creates no second Brief, and a cancelled Brief is not created again. The Owner moves, changes, and cancels it with the Schedule tools. A time zone change moves it with the other repeating Schedules.
- **Follow-ups.** The agent sets Follow-ups with `set_schedule`. Code sets `setBy: agent`, never the model. A Follow-up comes before the due date of an Open Loop, or after about a day with no change.
- **Untrusted Content.** A Turn for an Event with Trust Level `untrusted` gets no `set_schedule`, no Owner Preference tool, and no `mute_proactive_message`.
- **Evals.** There are no real-model Eval Cases for Open Loops, Follow-ups, Outcomes, or "less of this" now. This is a temporary path. The Evals come when the base set of MVP features works. Risk: the model can choose a wrong Open Loop or a wrong follow-up time, as #50 and #51 show for other tools.

### Decisions that later tickets build

- **Quiet Hours.** A fired agent Schedule in Quiet Hours makes no model call. The gate moves its due instant to the end of Quiet Hours in the local time of the Owner, also across a daylight saving change, and writes a `ProactiveMessageHeld` Journal Entry with the old and new instant. The Inbox key (Schedule id, due instant) stays the exactly-once rule: a held Schedule has a new due instant, so its next fire is a new key.
- **Send Budget.** The gate counts the Proactive Messages that were sent in the local day, from the Journal. At the Budget, a Follow-up folds into the next Brief. The Brief itself always runs. The Budget counts sends, not items.
- **Merge.** When the gate sends, it takes every other agent Schedule that is due within the merge window or held, and runs them as one Turn with all their Open Loops, so the agent writes one message. A Brief that is due within the window takes the Follow-ups.
- **Token Budget and active limit.** Over `proactiveDailyTokenBudget`, Follow-ups fold and make no model call. `maxActiveAgentSchedules` (20) is separate from `maxActiveScheduledTasks`.
- **Brief and Quiet Hours.** When the Owner changes Quiet Hours, the Brief keeps its own time unless it was at the old end of Quiet Hours. Then it moves to the new end.
- **Outcome connection.** Code connects the next Owner message to the last Proactive Message when it comes before the next Proactive Message and within the response window. The window includes its exact end: a message at the window is connected, one millisecond later is not. A second Proactive Message ends the connection. The connected Turn sees the Proactive Message and its Open Loops in its system prompt.
- **Outcome rules.** `acted`: an Open Loop of the message opens, changes, or closes in a connected Turn. `replied`: a connected Turn changes none. `muted`: the Owner says "less of this". `ignored`: no connected message in the window; code records it when the window ends, through the alarm of the Schedules store, with no model call. An Outcome is recorded once, the first rule wins, and `muted` replaces `replied` in the same Turn. A `ProactiveMessageOutcome` Journal Entry records it. No code rule stops Follow-ups after `ignored` Outcomes; the agent sees the recent Outcomes and changes its approach.
- **"Less of this".** The tool `mute_proactive_message` saves an Owner Preference: fewer Follow-ups for the Open Loops of the connected message (default) or for their kind. A muted Open Loop appears only in the Brief. "Stop" is different: it closes the Open Loop or cancels the Schedule. The Owner can undo it with the same tool.
- **Setting Follow-ups.** `set_schedule` with Open Loop ids, when the Owner did not ask for a Schedule in the Turn, gets `setBy: agent` from code. A link table connects Schedules to Notes.

### What ticket #102 builds

- **Proactive path.** A fired Schedule with `setBy: agent` and the `RunPrompt` Action goes to the proactive path, not to the Scheduled Task Turn. The Model Task is `proactive`. Its Usage rows, the Trace, and the Budget count use that name.
- **Tools of a proactive Turn.** It has the read tools (`search_notes`, `list_linked_notes`, `list_schedules`) and the Open Loop tools `list_open_loops` and `close_open_loop`. The system prompt allows a close only when the Notes already show that the Open Loop is done or dropped. It has no other tool that changes anything, and no Owner Preference tool.
- **Open Loops in reach.** Before the model call, code reads up to 20 open Open Loops, due first. It lists them in the system prompt and records their ids in the Proactive Message row. The row exists before the send, so a reset cannot change which Open Loops the message is about.
- **Proactive Message row.** The table `proactive_messages` has the Event id, the sent message id (null until the send is confirmed), the Open Loop ids, the Outcome (null while open), and the planned time. Recovery after a reset sets the sent message id from the Delivery state.
- **Token Budget.** `proactiveDailyTokenBudget` is read from Usage records of the Model Task `proactive`, as in [0017](0017-scheduled-task-limits.md). In this ticket the Brief always runs. The tokens spent before the Turn are in its Trace. A later ticket makes follow-ups fold when the Budget is spent.
- **Failure.** A proactive Turn that fails sends no failure notice, because the Owner did not ask for it. The Schedule completes before the Event is marked failed, so a reset between the two steps cannot leave the Brief at an old due instant. The Brief moves to the next day. A send that fails or is not confirmed also completes the Schedule. Recovery after a reset follows the same rules.
- **Lateness.** A Brief that fires late says when it was planned, as a Scheduled Task does.
- **Schema file.** `storage-schema.ts` is at the 250-line limit of the `max-lines` rule. The table `proactive_messages` is in `src/proactive/proactive-schema.ts`, and the Drizzle config of the Personal Agent lists both files. This supersedes the rule of 0007 that a store has one table schema file. The new rule: the table schema files of a store (`storage-schema.ts` and the files that its Drizzle config lists) are together its single source of truth, and each table is in exactly one of them. All other parts of 0007 stay.
- **Active limit.** The active limit `maxActiveScheduledTasks` counts only Schedules that the Owner set, so the Brief does not use the room of the Owner.
- **Records.** The Trace of a proactive Turn is written before the send, like every Trace, so a reset cannot lose it: the result `proactive_message_sent` says that the model answered and the message went to delivery. When the send fails or no Owner Channel Conversation exists, code appends a second Trace with the result `proactive_message_failed`, and the last Trace of the Event is the true one. A reset between the failed send and the second Trace leaves only the first Trace; the `ReplyFailed` Journal Entry is then the record of the failure. A model failure writes only `proactive_message_failed`. The Trace has the Budget and the tokens spent before the Turn. The Operator metric of the kind `proactive_message` has the Event id in `blob5` and no content. Recovery after a reset writes it again when it finds a confirmed send, so a reset never loses it and can repeat it; readers count distinct Event ids (0017). The Journal records `BriefCreated`.
- **Local proof.** `pnpm control request` with the fake model shows a Brief: the fake `brief soon` message moves the Brief to the next minute with the existing Schedule tools.

### What ticket #99 builds

- **The gate.** The module `src/proactive/proactive-gate.ts` decides every `ScheduleFired` Event of a Schedule with `setBy: agent` before any model call. Its result is a closed union, `Send` or `Hold`; the next tickets add `FoldIntoBrief`. When the time zone is not known, the result is `Send`, because no local time exists.
- **Quiet Hours range.** `start` and `end` are local `HH:mm`. The start is inside Quiet Hours and the end is not. A range with a start after the end crosses midnight. A start equal to the end is refused. The end of Quiet Hours is the next occurrence of the end time after the current instant, so a daylight saving gap moves it to the next real instant (disambiguation later, as in 0013).
- **Hold.** A hold moves the due instant of the Schedule to the end of Quiet Hours, appends `ProactiveMessageHeld` (Schedule id, old and new instant, reason `quiet_hours`), and writes a Trace with the result `proactive_message_held` in one transaction. The Event is then done. A hold of an Event that has a `ProactiveMessageHeld` entry reuses its new instant and adds no second entry or Trace, so a reset or a second alarm run gives one hold. No Operator metric for a hold is added in this ticket.
- **Source of a preference.** `owner_preferences` has a `source` column. It is free text in storage, with no check on its values, and `owner` is the only value that code accepts now. A new source is a code change and needs no migration. A preference that the Owner stored always wins over the default.
- **The tool.** `quiet_hours` reads the Quiet Hours with no input and changes them with both `start` and `end`. Only an Event with Trust Level `owner` gets it. In the same transaction as the write, a Brief that is active and repeats Daily at the old end moves to the new end; a Brief at another time stays. The Brief is the Schedule of its `BriefCreated` Journal Entry.
- **Brief creation.** `set_time_zone` creates the Brief at the end of the Quiet Hours that apply to the Owner, not always at the default end.
- **Tests and the real clock.** The Worker tests use Quiet Hours around the current time because the Durable Object uses the real clock. The table test of the pure function proves the 22:00 to 08:00 and daylight saving cases.

### What ticket #100 builds

- **Connection at receive time.** When an Owner message arrives, one transaction stores it in the Inbox and connects it to the last sent Proactive Message that has no Outcome, no connected message, and a response window that has not ended. The message that arrives at the exact window end is connected. A message that arrives one millisecond later is not. Only the last sent Proactive Message can be connected, so a second Proactive Message ends the connection to the first. Only the next Owner message connects: after it, the message has an Outcome and later messages are normal messages. The decision is made at receive time, so a Turn that runs late connects as it would have run on time, and a restart cannot change it.
- **Table.** `proactive_messages` gets the sent instant, the end of the window, and the connected Owner message Event id. The window length is the Behavior Config value `proactiveResponseWindowMillis` (24 hours). Recovery after a reset sets the sent instant with the sent message id, so a recovered send can have a later sent instant than the real one.
- **Connected Turn.** The system prompt of a connected Turn says that the message follows a Proactive Message, quotes the text from the Delivery state, and lists its Open Loops with the kind, state, due time, and text. The prompt says to treat the message as an answer when it fits, and as a normal message when it does not.
- **Recording `acted` and `replied`.** When the Turn loop is done with a connected Owner message (also after a recovery that finds the reply already sent, and also after a failed Turn), code reads the Journal Entries of that Event. A `OpenLoopOpened`, `OpenLoopChanged`, or `OpenLoopClosed` entry for an Open Loop of the Proactive Message gives `acted`. No such entry gives `replied`. The `muted` rule of a later ticket reads the same entries and replaces `replied`. The Inbox marks the Event done before the Outcome is recorded, so a reset between the two leaves a connected Event outside the Inbox with no Outcome. Code settles such Events at the start of every Turn run and when the alarm runs. The alarm of the Schedules store stays armed while a connected Event has no Outcome: at once when the Event left the Inbox, and one minute ahead (and again one minute later) while it is still pending. A Schedule change or a reset between the Inbox write and the Outcome therefore cannot leave the Outcome without a trigger.
- **Recording `ignored`.** The alarm of the Schedules store is also armed one millisecond after the earliest window end of a sent message that has no Outcome and no connected Owner message. When the alarm runs, code records `ignored` for each message whose window has ended, before the due Schedules fire. No model call is made. The alarm callback records the Outcome first and arms the alarm again at the end, so an Outcome that is recorded does not leave a stale alarm.
- **Once.** An update that needs `outcome IS NULL` and the `ProactiveMessageOutcome` Journal Entry are in one transaction, so a second alarm run, a recovery, or a repeated recording writes nothing. The Operator metric of the kind `outcome` (the result is the Outcome, the Event id of the Proactive Message is in `blob5`, the latency is the time from the send) is written after the transaction. A reset between the two can lose the data point. The Journal is the record.
- **Recent Outcomes.** A proactive Turn shows the last three Outcomes of earlier Proactive Messages for each of its Open Loops in reach, and its system prompt says: when the Owner keeps ignoring an Open Loop, change the approach (another time, a smaller step) or ask why. No code rule stops Follow-ups.
- **Known limit.** An Owner message that arrives between the real send of a Proactive Message and the write of its sent instant (the Turn is still running) is not connected to it.

### What ticket #105 builds

- **Preference.** `muted_proactive_messages` is a new Owner Preference (source `owner`): a set of Open Loop ids and a set of kinds. A kind is stored trimmed and in lower case, and an Open Loop matches when its kind, normalized the same way, is in the set. The CHECK of `owner_preferences` and of `turn_traces` change in one migration.
- **The tool.** `mute_proactive_message` has the actions `mute`, `undo`, and `list`, and the scopes `open_loops` (default) and `kind`. Code resolves the target: with no `openLoopIds` and no `kind`, it uses the Open Loops of the Proactive Message that the Turn is connected to (and their kinds, for scope `kind`). With no connected message and no target, it fails with a message for the model. Only an Event with Trust Level `owner` gets it, so a proactive Turn and a Turn for an untrusted Event have none. Each `mute` or `undo` call appends a `ProactiveMuteChanged` Journal Entry, also when the stored value did not change, in the same transaction as the write. `list` changes nothing and appends nothing.
- **Which scope.** When it is not clear whether the Owner means the Open Loops of the message or their kind, the agent saves the default (the Open Loops of the message) in the same Turn and asks one short question whether to cover the whole kind. No answer therefore leaves the default saved, and no timer or code state is needed.
- **Outcome.** In the connected Turn, a `ProactiveMuteChanged` entry with the change `muted` gives `muted`. The order is `acted`, then `muted`, then `replied`: a Turn that also changes an Open Loop of the message records `acted`, as the first rule wins.
- **The gate.** The result `FoldIntoBrief` (reason `muted`) is new. A follow-up whose open Open Loops are all muted (by id or by kind) gets it, before the Quiet Hours check, because it sends nothing. It makes no model call. Code completes the Schedule, appends a `ProactiveMessageFolded` Journal Entry, and writes a Trace with the result `proactive_message_folded` in one transaction. A second run for the same Event writes nothing. The Brief lists first the open Open Loops of the `ProactiveMessageFolded` entries that no later Proactive Message has listed (from the Open Loop ids that each `proactive_messages` row stores, so a reset cannot lose or repeat them), then the earliest due open Open Loops, up to 20 together, so a folded Open Loop is named in the next Brief even when more than 20 are open. If the Send Budget ticket (#104) adds the same result, its path replaces this completion and keeps the reason `muted`.
- **Mixed follow-ups.** A follow-up with some muted and some unmuted Open Loops is sent. Its proactive Turn lists only the unmuted ones, and its system prompt names the muted ids and says not to write about them, even when the stored prompt does.
- **`set_schedule`.** A follow-up that names a muted Open Loop is refused with a message for the model. A Schedule that the Owner asked for is not refused.
- **Undo.** `undo` removes the ids or the kinds that the same selectors give. Undoing an id does not remove a mute of its kind, and the result lists what is still muted. `list` shows the muted ids with their text and the muted kinds.
- **Evals.** There is still no real-model Eval Case for "less of this" (see Evals above).

## Why

The MVP promises that the agent comes to the Owner first. Limits in code keep that useful and not annoying, and the recorded Outcomes let the Operator tune the behavior. A Brief with its own Schedule and its own Model Task needs no new scheduler: it uses the Schedules store, the alarm, and the exactly-once rules that exist.

## Revisit if

- Real Outcomes show that the defaults are wrong.
- A second source (a Profile, sleep data) sets Quiet Hours.
- Habits or MCP items need more Open Loop state than `open` and `closed`.
