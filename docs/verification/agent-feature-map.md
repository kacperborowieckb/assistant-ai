# Feature Map: apps/agent

Generated from `apps/agent/src/edge/routes.ts` by `pnpm control map`. Do not edit this file. `pnpm control map --check` fails when it is out of date.

| Route | Access | Purpose |
| --- | --- | --- |
| `POST /telegram/webhook` | Telegram secret token in X-Telegram-Bot-Api-Secret-Token | Receives a Telegram update, finds the Owner through the Directory, and stores the Event in the Owner's Personal Agent before it answers 200. |
| `POST /operator/owners` | Operator token as Authorization: Bearer | Adds an Owner with a Telegram Channel Identity through the Directory. Registration stays closed. |

## Seed and navigation

1. Run `pnpm control dev`. It applies the Directory migrations to local D1 and starts the Worker with a fake Telegram API and a fake model.
2. Run `pnpm control owner add --telegram-user <id>` to seed the Owner through `POST /operator/owners`.
3. Send a Telegram update to `POST /telegram/webhook` with the `TELEGRAM_WEBHOOK_SECRET` from `.dev.vars`. The `dev` output shows the fake `sendMessage` reply. Before the reply, the Personal Agent shows the typing signal with Telegram `sendChatAction` (`typing`), at once and about every 4 seconds until the reply or the reaction is delivered or the Turn stays silent; Reminders, Scheduled Tasks, and Proactive Messages show none.

`pnpm control request --contains <text>` runs steps 1 to 3 with temporary storage and checks the reply. It prints the fake `sendChatAction` calls that each message got before its reply. Without `--contains`, it shows what the agent sent, including a reaction or no send.

## One answer per Burst

Several Owner messages sent close together get one answer. An Owner message does not start a Turn at once: the Personal Agent stores it, shows typing, and waits until no new message came for `burstQuietMillis` (2.5 seconds), or until `burstMaxWaitMillis` (10 seconds) after the first message. Then one Turn takes every pending Owner message in arrival order and delivers one outcome in reply to the newest message. A later value replaces an earlier one. A Schedule that is due during the wait still fires on time. Example: `pnpm control request --burst --message "todo: buy milk" --message "ok"` sends both messages at once and shows the typing signal and one outcome for the Burst (silence, because the fake model answers the newest message).

## Silence for small talk

Each Owner message Turn ends in one outcome. A final text is a reply. For small talk such as "ok" or "thanks", the model calls `stay_silent`: code makes no Channel call, and the Journal records `StayedSilent`, so recovery never sends later. Code refuses `stay_silent`, and the model gets the refusal as the tool result, when a tool call in the Turn changed Owner data or a changing tool call failed. A failed model call still sends the honest failure text. A proactive Turn, a Scheduled Task Turn, and a Turn for an untrusted Event have no `stay_silent`. In the local fake model, `ok` stays silent. Example: `pnpm control request --message "keep: buy milk" --message "ok"` shows the reply to the first message and no send for the second.

## Reactions

The model can also answer with one emoji reaction and no text: it calls `react`, and the Telegram Channel sets the reaction with `setMessageReaction` on the newest Owner message of the Burst. An emoji that Telegram does not allow bots to use becomes a close match or the default reaction 👍, and the Trace records the replacement. Code refuses `react` after a changing tool call failed, and reacts with 👍 when a Turn that changed Owner data ends with no text and no outcome. Recovery sends an unconfirmed reaction again. `react` is absent where `stay_silent` is. In the local fake model, `react: <emoji>` reacts with that emoji. Example: `pnpm control request --message "react: ✍️" --message "react: 🦖"` shows the reaction ✍ on the first message and 👍 on the second.

## Open Loops in the chat

A Note that is something to come back to has an Open Loop, with the tools `capture_note`, `update_note`, `close_open_loop`, and `list_open_loops`. In the local fake model, `todo: <text>` keeps a Note with an open Open Loop of kind `task`, `what is open?` lists the open Open Loops, and `done: <words>` closes the first open one that contains the words. Example: `pnpm control request --message "todo: buy a gift for Ana" --message "done: gift" --message "what is open?" --contains "Open (0)" --wait-for-later-message=false`.

## Schedules in the chat

The Owner sets, lists, changes, and cancels Schedules (Reminders, with the `SendText` Action) through the Telegram webhook, with the tools `set_schedule`, `list_schedules`, `change_schedule`, and `cancel_schedule`. In the local fake model, a message that starts with `zone: <IANA name>` sets the time zone, `remind: <text>` sets a Reminder for the next minute, `remind daily: <text>` sets a Daily repeating Reminder for the next minute (it stays active and moves to the next day after it is sent), and `cancel reminder: <words>` lists the Reminders and cancels the first one that contains the words. Example: `pnpm control request --message "zone: Europe/Warsaw" --message "remind: buy the gift" --message "cancel reminder: buy the gift" --contains "Cancelled Reminder: buy the gift" --wait-for-later-message`.

## The Brief

When the Owner's time zone becomes known for the first time, code creates the Brief: a Daily `RunPrompt` Schedule with `setBy: agent` at the end of the default Quiet Hours (08:00 local). When it fires, the agent runs a proactive Turn (Model Task `proactive`) with read tools, `list_open_loops`, and `close_open_loop`, and sends one message to the Owner Channel Conversation. The Owner moves, changes, or cancels the Brief with `list_schedules`, `change_schedule`, and `cancel_schedule`. A second time zone change creates no second Brief, and a cancelled Brief is not created again.

In the local fake model, `brief soon` moves the Brief to the next minute, and the fake model answers its proactive Turn with `Brief: <n> open Open Loops`. Example: `pnpm control request --message "zone: Europe/Warsaw" --message "todo: buy a gift for Ana" --message "brief soon" --contains "Brief: 1 open Open Loops" --wait-for-later-message`.

## Quiet Hours

No Proactive Message arrives in the Quiet Hours of the Owner (default 22:00 to 08:00 local). The Owner reads and changes them in the chat with the tool `quiet_hours`, and a Brief at the old end moves to the new end. When a Schedule that the agent set fires in Quiet Hours, code makes no model call and moves it to the end of Quiet Hours. Reminders and Scheduled Tasks that the Owner set still arrive. The local fake model has no message for Quiet Hours; the Worker tests in `test/quiet-hours.test.ts` prove the hold.

## Less of this

When the Owner says "less of this" right after a Proactive Message, the agent calls `mute_proactive_message`: it mutes the Open Loops of that message (the default), or their kind. A muted Open Loop gets no follow-up of its own: the gate folds it with no model call, `set_schedule` refuses a new follow-up for it, and it appears only in the Brief. The connected Proactive Message records the Outcome `muted`. The Owner undoes a mute in the chat. A Turn for an untrusted Event and a proactive Turn have no `mute_proactive_message`. The local fake model has no message for it; the Worker tests in `apps/agent/test/less-of-this.test.ts` prove it.

## Follow-ups

In a proactive Turn, the agent sets its own next follow-up with `set_schedule`: a `RunPrompt` Schedule with `openLoopIds`. Code sets `setBy: agent` because the Owner did not ask for a Schedule in that Turn, or in an owner message Turn when a call has `openLoopIds` and no `ownerAskedForSchedule`; the model never sets `setBy`. At most `maxActiveAgentSchedules` (20) agent Schedules are active, and Scheduled Tasks that the Owner set are not counted. `list_schedules` shows `setBy` and `openLoopIds`. A Turn for an untrusted Event has no `set_schedule`. The local fake model does not set follow-ups; the Worker tests in `apps/agent/test/follow-ups.test.ts` prove them.

## The send Budget

The agent sends at most a set number of Proactive Messages per local day of the Owner (default 3). The Owner reads and changes the Budget in the chat with the tool `proactive_message_budget`, and the stored value has the source `owner`. When the Budget or `proactiveDailyTokenBudget` is used up, a follow-up that the agent set makes no model call and folds into the next Brief, and the Brief names its Open Loops. The Brief itself always runs. With no active Brief, the follow-up is skipped and recorded. The local fake model has no message for the Budget; the Worker tests in `test/send-budget.test.ts` prove the fold.

## Merged follow-ups

Many Open Loops do not mean many messages. When the agent sends a follow-up, it takes every other follow-up that is due within the next 30 minutes (`proactiveMergeWindowMillis`) into the same Turn, and writes one message. The merged follow-ups complete or move to their next occurrence after that one send, and the merge counts as one send for the Budget. A follow-up that fires when the Brief is due within 30 minutes folds into the Brief. Follow-ups that Quiet Hours held merge into one message at the end of Quiet Hours. The local fake model does not set follow-ups; the Worker tests in `apps/agent/test/merge.test.ts` prove the merge.

## Scheduled Tasks in the chat

A Scheduled Task is a Schedule with the `RunPrompt` Action. At the due time, the agent runs a Turn with the stored prompt and sends the result.

In the local fake model, `task: <prompt>` sets a Scheduled Task for the next minute. `task daily: <prompt>` sets a Daily repeating one. The fake model answers its Turn with `Scheduled task result: <prompt>`. Example: `pnpm control request --message "zone: Europe/Warsaw" --message "task: list my notes" --contains "Scheduled task result: list my notes" --wait-for-later-message`.
